# Database design and operator procedures

The application uses Supabase Auth and PostgreSQL. `supabase/migrations` is the authoritative, ordered schema. Apply it to separate development, staging, and production Supabase projects. Use a restricted migration operator; do not give the web runtime DDL privileges. Pool application connections, require verified TLS for remote PostgreSQL, and place backups outside the web/static root.

Run `supabase start` and `supabase db reset` when Docker and the Supabase CLI are available. Local callback allowlists are in `supabase/config.toml`. Never copy local callback URLs or synthetic seed records into a production migration. `supabase/seed.sql` contains only explicitly synthetic, inactive records and no users, passwords, memberships, admin records, consent grants, active trial, paid subscription or verified phone.

## Boundaries

Every business-owned row has a non-null `business_id`. Cross-table links use composite `(business_id,id)` foreign keys. The only records without a business key are the platform-wide admin registry and pre-authentication rate buckets under the private schema. They do not confer tenant membership.

All application tables enable RLS. Anonymous access has no table privileges. Authenticated clients receive bounded read privileges with membership predicates, and column-specific profile/notification updates. The membership predicate verifies the current user against database memberships, confirmed email, suspension, ban state, and business suspension; it does not use caller-provided role metadata. Its pinned `SECURITY DEFINER` function avoids recursive membership policies. Service roles bypass RLS, so the worker and webhook adapters must include `business_id` in every operation.

Provider secrets, refresh-token ciphertext, webhook payloads, outbox data, consent evidence, suppression records, invitations, and trial identity hashes have no authenticated table grants. Authenticated users cannot set billing state, trial verification, phone assignment, provider identifiers, ownership, membership roles, or entitlements. Browser writes use explicitly allowlisted fields and bounded RPCs.

Owners manage business settings, invite staff/viewers, remove members and activate an eligible trial. Owners and staff take over conversations, send manual intents, request callbacks and confirm lead outcomes. Viewers read tenant data. Direct insert/delete grants are intentionally absent: functions enforce authorization and workflow semantics. A last-active-owner trigger rejects removal, demotion and suspension of the final owner, including privileged worker writes. Staff/viewer invitations cannot grant owner access. Ownership transfer currently requires an audited restricted operator procedure.

## Function contracts

- `create_business(p_name,p_timezone,p_zip_codes)` requires a verified account, validates IANA timezone and ZIP codes, caps memberships, then atomically creates business, owner membership, profile, inactive entitlements, subscription, and audit event.
- `take_over_conversation(p_business_id,p_conversation_id,p_mode)` accepts `ai` or `human`, requires owner/staff, scopes both IDs and acquires a row lock. It refuses while a bounded provider dispatch is in progress.
- `enqueue_manual_message(p_business_id,p_conversation_id,p_body)` requires human mode and owner/staff. It inserts a pending human message and a `sms.send` outbox record in one transaction. The worker still enforces suppression, consent, registration, quiet hours, entitlement, and budget before dispatch; enqueuing is not delivery.
- `update_lead(p_business_id,p_lead_id,p_status)` allows `new`, `needs_callback`, `qualified`, `won`, `lost`. Only an owner can confirm `won`, and the account/timestamp are recorded. Only verified calendar success can create a booked outcome; manually marking a lead won does not create invented revenue.
- `create_callback(p_business_id,p_lead_id,p_note)` records a notification and callback-needed state without sending an SMS.
- `create_invitation(p_business_id,p_email,p_role,p_token_hash)` accepts staff/viewer only. The server generates at least 32 random bytes, returns the secret invitation link only through an authorized owner response, and stores a SHA-256 hash. `accept_invitation(p_token)` locks the invitation, verifies account email, expiry and single use, and consumes it atomically.
- `remove_member(p_business_id,p_membership_id)` is owner-only and audited; the last-owner trigger still applies.
- `activate_trial(p_business_id)` is owner-only and derives a trial identity from a server-verified forwarding destination. The underlying two-argument routine is service-only and requires verified business, verified destination, enabled routing, approved messaging registration, a passed live test, and unused identity. The identity hash is only a proportionate duplicate check: operators must verify business authorization and review suspected circumvention. Support overrides require restricted operator review and must be audited.
- `persist_webhook(p_business_id,p_provider,p_event_key,p_payload,p_topic)` and `ingest_webhook(...)` are service-only. They insert deduplicated event and outbox record atomically. The caller verifies the provider signature and resolves business through trusted provider-account/number records before invoking them. They never authorize a browser-supplied business ID.
- `reserve_usage(p_business_id,p_kind,p_idempotency_key,p_quantity)` is service-only and locks the entitlement row, deduplicates reservations, checks current state/expiry and hard caps, then reserves quota atomically. Reservations need provider reconciliation/settlement; ambiguous outcomes must not be released and resent blindly.
- `consume_rate_limit(p_key,p_limit,p_window_seconds)` is service-only. It uses shared database fixed-window buckets and returns `allowed`, `remaining`, and `retry_after`. Callers hash IP/account signals and do not trust arbitrary forwarded headers. A gateway must limit malicious unauthenticated traffic before it can fill the table; periodically delete expired buckets through a restricted maintenance job.
- Mutation triggers in `0005_rpc_throttles.sql` enforce separate database-user/action/tenant buckets for profile, invitations, human message intents, mode changes, appointments, notifications, member removal and lead writes. They prevent bypassing gateway limits through direct authenticated Supabase calls. Trusted worker operations have no user claims and remain subject to explicit budgets, admission gates and queue limits. A custom `PT429` error represents a throttled database mutation.
- `check_platform_admin()` requires an explicitly bootstrapped private registry entry and provider JWT assurance `aal2`. `admin_pause_automation(p_business_id,p_reason)` additionally requires the operator role and records the reason. Contractor ownership grants no platform role.

## Consent and trial activation procedure

An incoming call never inserts a consent grant. Where there is no approved evidence, capture the enquiry and request a manual callback. Before creating consent evidence, obtain business/provider/legal approval for the disclosure, sender, service-recovery scope and explicit re-opt-in process. A restricted operator records only the necessary evidence reference, source, sender number, policy version, grant timestamp and any expiry. STOP creates durable suppression even when jobs were previously queued. Clearing a suppression requires evidence; a generic START message is not an automatic local re-opt-in implementation.

Configure Twilio on an isolated provider account, verify the forwarding destination and business authorization, restrict geography to approved US destinations in Twilio and the app allowlist, and verify no routing loop. `+1` alone is not a US-only guarantee. Complete messaging registration and a real provider sandbox/live test under approved consent before an operator records verification and `live_test_passed_at`. Setting these fields is deliberately not a browser capability. Trial begins only after these records are present. Missing entitlement leaves automation disabled while routing and suppression processing can continue.

## Provider purchase and appointment operations

`begin_phone_provisioning(p_business_id)` records a service-only acquisition intent before the provider request. A unique per-business ledger and phone constraint prevent repeated purchases. `finish_phone_provisioning(p_operation_id,p_business_id,p_provider_account_id,p_sid,p_phone)` atomically binds a proven provider result to the trusted tenant account and completes the operation, with idempotency for the identical result. `mark_phone_provisioning_unknown(...)` blocks retries after ambiguous provider acceptance. Reconcile provider inventory in a restricted operator session before clearing an intent or releasing an orphaned number. New numbers are never automatically routing-enabled or registration-approved.

`request_appointment(p_business_id,p_lead_id,p_start_at,p_note)` is authenticated staff/owner-only and stores an unconfirmed request for a 60-minute future inspection within 90 days, business hours and the 15-minute buffer. Disabled days are honored. `confirm_appointment(p_business_id,p_appointment_id,p_evidence_hash)` is service-only and is invoked only after server-verified, explicit customer confirmation using the signed one-time link flow. It locks the request, records minimized evidence, binds the active calendar connection, then creates a single `calendar.book` outbox entry. Missing calendar leaves an honest requested callback. Provider creation and local persistence are necessary before confirmed status. Unknown provider outcomes continue reserving the slot.

`businesses.automation_hold_at` records an operator circuit breaker. `subscriptions.review_required_at` records persistent billing-risk review. Ordinary renewal/payment reconciliation must not clear these flags or grant work while they are set. An audited restricted operator must investigate and explicitly clear a hold; there is no browser-owned override. `reserve_usage` rechecks these flags even if an entitlement row otherwise appears active.

## Admin bootstrap

In an authorized operator SQL session, select the intended confirmed Supabase user by its exact verified ID and insert that UUID with `role='operator'` into `private.platform_admins`. No email substring, default password, first-user promotion, public admin signup or browser flag is used. Enroll TOTP through Supabase Auth and verify `aal2` before opening the admin area. Revoke access by setting `revoked_at`; no restart is required. Record the bootstrap/revocation in an operator-controlled security log. Audit-only admins can view bounded health metadata through the authenticated server layer; they cannot pause automation.

## Retention, backup and restore

Set retention with the actual business's privacy commitments and provider requirements before launch. Recommended initial review targets are 30 days for raw webhook payloads, 90 days for ordinary message bodies and operational attempts, and longer retention only where justified for consent/suppression or billing evidence. These are proposed settings, not automatic legal compliance claims. No automatic destructive deletion is enabled. Suppression tombstones must survive ordinary contact cleanup to avoid re-enabling revoked messaging. Use a restricted, documented account deletion workflow with processor deletion and number-offboarding review.

Enable the hosting provider's encrypted backups/PITR. Keep the backup encryption key and database credentials in the host secret manager. To run a restore drill, create an isolated staging Supabase project with messaging, billing and workers disabled. Restore a provider-supported backup/PITR snapshot using that provider's process; never place a dump in `public/`, Git, a CI artifact or a browser download. Apply missing versioned migrations, validate row counts and tenant foreign keys, rerun the database tests against the staging environment with synthetic fixtures, and verify RLS through real authenticated API sessions for two tenants and all roles. Verify queue/outbox reconciliation, suppression retention, and idempotency before enabling any worker. Record snapshot time, recovery point, duration, migration SHA, measured RPO/RTO, failures and operator signoff. Switch application URLs only after approval; retain the old environment for rollback according to the retention policy.

**Restore status: NOT VERIFIED against hosted Supabase.** Embedded database tests validate migrations and policy behavior under a real WASM PostgreSQL engine, not a managed-provider backup or hosted Auth. A production restore drill is a launch gate.

## Automated evidence and limits

`npx vitest run tests/database.test.ts` applies all versioned migrations in an ephemeral PGlite database with the maintained pgcrypto extension, creates synthetic tenants and role identities, and executes real SQL authorization, RLS, constraint and RPC checks. It tests tenant read boundaries, forbidden writes, nested cross-tenant IDs, privilege escalation, unverified/banned accounts, invitation binding/single use, admin MFA claims, last-owner protection, webhook/outbox deduplication, usage cap/idempotency/expiry, shared limiter behavior, and routing loops. It does not substitute for hosted Supabase HTTP tests, cryptographic JWT/session verification, multi-process lock contention, backup/PITR, queue restarts or provider acceptance tests.
