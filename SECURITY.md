# Security model and operating limits

This document describes implemented controls and remaining verification. It is not an independent penetration test, certification, provider approval or legal-compliance finding. Launch depends on the root checklist and actual staging acceptance tests, not on this document alone.

## Threat model

Protect customer contact details/messages, tenant configuration, consent evidence, provider credentials/tokens, money/usage budgets and account authority. Relevant attackers include unauthenticated web clients, malicious or compromised tenant users, forged/replayed provider requests, hostile SMS/prompt input, compromised devices/sessions and misconfigured privileged operators. The browser, caller-supplied tenant IDs, AI output, source text and integration responses are untrusted. Provider signing keys, the restricted migration/operator role, deployment secret manager and Supabase's JWT verification boundary are trusted infrastructure with their own operational controls.

| Threat                          | Control                                                                                                                             | Limit requiring verification                                                 |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Cross-tenant reads/IDOR         | Verified server identity, membership checks, RLS, composite tenant FKs and scoped service queries                                   | Hosted user-token HTTP regressions and independent review                    |
| Role/admin elevation            | No direct role/ownership grants, staff/viewer-only invites, last-owner trigger, private admin registry, verified aal2               | Operator bootstrap/revocation and real MFA enrollment drill                  |
| Revoked sessions                | Signed session ID must still exist for that user in `auth.sessions`; normal backend calls provider getUser                          | Hosted global signout/reset/revocation and provider timeout behavior         |
| Forged/replayed webhooks        | Twilio SDK signatures over exact configured external URL/form, Stripe raw-body signature/tolerance, trusted mapping, durable dedup  | Reverse-proxy canonical URL configuration and sandbox provider tests         |
| Unsolicited or post-STOP sends  | No call-derived consent; admission suppression, dispatch recheck, approved sender/contact flags, quiet-hour/cap checks              | Legal/provider policy approval, country/line-type lookup, real opt-out tests |
| Expensive automation            | Atomic usage reservation, bounded AI context/output/turns and daily reserves, hard-cap pause, ordered queue                         | Provider account spend limits/alerts and measured model-cost settings        |
| Duplicate provider side effects | Durable send/purchase intents, unknown outcomes block blind retries, deterministic calendar IDs                                     | Real timeout/restart and operator reconciliation drills                      |
| Prompt injection                | Extraction model has no tools, secrets, tenant selector or booking authority; strict parsed facts; deterministic outbound templates | Real pinned-model adversarial evaluation and human review                    |
| Stored/reflected XSS            | React text rendering, strict input sizes, no executable customer Markdown/HTML                                                      | Browser CSP/XSS regression suite and actual enforced headers                 |
| CSRF/cross-origin mutation      | Exact Origin check, JSON content type, bounded strict schemas, safe methods; protocol-specific OAuth state and webhook signatures   | Deployed gateway origin handling and staging cross-origin tests              |
| SSRF                            | Server-selected fixed provider HTTPS hosts and rejected redirects; no arbitrary business URL fetch                                  | Host/network egress enforcement and provider hostname configuration          |
| Secret disclosure               | Server-only modules, environment schemas, generic SDK errors, ignored real env files, token encryption and redacted scanning        | Actual scanner/history/build-bundle evidence and operator key management     |

Auth credentials are passed directly to Supabase Auth. The app does not store custom passwords or rehash them before sending to the provider. The initial policy is at least eight characters with a letter and number to match the supplied account-access specification; enable the provider's supported leaked/common-password protection and review stronger business policy before launch. Signup/recovery responses avoid account enumeration. Shared database throttles cover authentication/account/IP signals and mutations; a correctly configured trusted gateway must strip spoofed forwarding headers. Without a trusted client-IP signal, pre-auth limits intentionally share an untrusted-source bucket and may constrain availability.

Server-side Supabase cookie storage is HttpOnly, SameSite=Lax, restricted to `/`, and Secure in production. This implementation routes browser auth through server handlers and does not create a browser Supabase client or store bearer/refresh tokens in localStorage. The provider SDK refreshes cookies in writable route-handler contexts. Read-only server components cannot write refreshed cookies. Signed purpose-bound cookies protect password-recovery grants and Google OAuth state/PKCE; safe redirect allowlists reject external/protocol-relative destinations. OAuth/email callback GETs are explicit protocol exceptions to POST-only business mutations.

## Secrets and encryption

Enter real credentials in ignored local `.env.local` or the deployment host's secret manager. Never paste secrets into chat or commit them. Public Supabase URL/publishable key are intentionally public with RLS; service-role keys, database URL/password, Twilio auth token, AI key, Stripe key/signing secret, Google client secret, cookie signing secret and token encryption key are server-only. Optional providers require explicit enable flags and valid configuration; production does not silently substitute synthetic success.

Stored provider/OAuth tokens use Node's maintained AES-256-GCM facility with random nonces and additional authenticated data binding the key version and tenant. The key remains separate from ciphertext in deployment secrets. The current adapter accepts one active key version and fails closed on unknown versions. A seamless multi-key rotation service is not implemented: perform an audited staging-tested decrypt/re-encrypt migration while the old key is available, or add an approved dual-read/current-write keyring before rotating active production tokens. Do not discard the old key before every required ciphertext has been migrated and verified. Cookie signing key rotation invalidates existing purpose-bound grants; handle that expected user reauthentication explicitly.

If scanning discovers a credential, never print its value. Remove the affected source/artifact exposure and identify the provider and redacted location. Rotate/revoke the actual credential in Supabase/Twilio/OpenAI/Stripe/Google or the hosting secret manager as appropriate. A deleted file does not revoke leaked credentials. Audit access logs and affected deploy artifacts, verify new credentials, invalidate compromised sessions, and document the incident. Shared Git history rewrite, force push and live revocation require explicit operator authorization.

## Messaging, billing and booking safety

Consent evidence is service/operator-only and must include approved scope, sender, source, policy version, timestamp and minimized evidence reference. A missed call is never consent. `contacts.sms_eligible` defaults false and can be set only after approved geography/line validation. `+1` includes destinations outside the US; restrict Twilio geographic permissions and a reviewed destination allowlist before enabling routing. STOP/21610 updates local suppression before admission acknowledgement. HELP and START create appropriate review; START does not silently clear local suppression. Unknown submissions retain reservations and require reconciliation before any retry.

Provider state and accepted checkout terms control billing. No entitlement comes from a success URL, client role, subscription-created event or zero-value invoice. Keep pricing/usage/first-charge/cancellation terms visible and verify merchant availability, especially for an India-based entity. Test mode never means real funds were collected. Administrative automation holds and payment-risk review must survive ordinary subscription reconciliation; clearing them requires restricted, audited review. Quiet-hour, entitlement, suppression and human-handoff checks still apply to manual SMS sends.

Inspection requests require an explicit customer-confirmation POST before a worker can create a calendar event. Customer confirmation tokens expire, are bound to one business and appointment, and are consumed through atomic appointment state. Before provider creation, the worker must check current entitlement and availability, approved hours, duration, buffer and customer confirmation. A confirmation link/request is not a confirmed booking. Unknown provider outcomes retain application slot protection and use deterministic event reconciliation. External calendar edits can still race application checks; no perfect external-lock guarantee is claimed.

## Admin bootstrap and operational access

Bootstrap only the exact verified Supabase user ID into `private.platform_admins` through a restricted operator session, then enroll/verify TOTP. There is no public admin signup, email-pattern rule, hardcoded password or first-user promotion. API authorization checks the provider's current identity/MFA and private registry for every support action. Contractor owner and platform operator are separate roles. Support requests require a reason and audit event and expose only bounded operational metadata. The platform auditor cannot invoke pause. Revoking registry access or tenant membership takes effect through database checks without a server restart.

Keep web and worker deployment principals separate from migration/backup operators. The worker needs scoped DML/function access plus its pg-boss schema rights; do not run it as the database superuser or grant web code arbitrary DDL. Privileged SQL bypasses RLS, so query review and explicit tenant scoping remain mandatory. Global maintenance is trusted internal work and is not exposed through a browser endpoint. Run processes without root where supported, enforce TLS, isolate staging resources, and restrict production egress/provider keys.

## Retention, recovery and incident response

Agree retention and subprocessors with the business before launch. Minimize raw webhook and message storage; preserve justified consent/suppression/billing evidence. No automatic destructive retention job is enabled before policy approval. Offboarding must separately address phone-number retention/release, existing forwarding, processor data, exports, backups and suppression continuity. Do not release a number merely because automation or billing stops.

Use encrypted provider backups/PITR and run the isolated restore procedure in `docs/DATABASE.md`. Hosted restoration and measured RPO/RTO remain NOT VERIFIED. During an incident, use the audited admin hold and provider-level kill switch to stop automation while retaining call routing and opt-out handling. Preserve redacted evidence, reconcile unknown sends/purchases/bookings, rotate affected secrets with authorization, restore in isolation if needed, and record root cause, customer impact and corrective tests. Avoid logging complete SMS text, email bodies, auth headers, signed links, connection strings or provider SDK error objects.

Automated local evidence includes real PostgreSQL-in-WASM migrations/RLS/RPC regressions with synthetic Auth stubs. That does not verify hosted JWT cryptography, managed Auth transport, provider approvals/delivery/payment/booking, or infrastructure isolation. Root `SECURITY_AUDIT.md` and `SECURITY_CONTROL_MATRIX.md` must report actual commands and results, including skipped checks and failures. Arrange an independent review before broad production launch.
